How we made the migration

  1. Create the destination schema. Django’s existing migrations built the PostgreSQL tables and generated permissions/content types. We kept the Django models and their historical tasks_ table names.
  2. Test PostgreSQL independently. On dev-postgres-tests, all 160 backend tests passed using Django’s temporary test database. A test-only response cleanup issue was fixed; application connection handling was unchanged.
  3. Take a consistent SQLite backup. SQLite’s backup API created a snapshot under ignored .backups/. PRAGMA integrity_check passed. We also checked that non-session local records still matched before the main import.
  4. Rehearse on a separate branch. We created dev-data-transfer from main. Separate credentials kept the workspace’s main connection intact.
  5. Import and compare inside a transaction. The script loaded records with preserved IDs and relationships, compared the result with the snapshot, and committed only after a match. Failure rolled back imported records.
  6. Repeat against main. The same snapshot passed the destination checks, import and comparison on main. Django API and image-route checks followed. The temporary rehearsal branch and its credential file were then removed.
Two details the rehearsal caught

Dependency ordering: users must load before admin-history records that reference them. We use Django’s dependency sorter so natural foreign keys resolve correctly.

Timestamp precision: Django’s standard JSON encoder trims datetime precision to milliseconds. The transfer uses Python serialization and an encoder that preserves full microseconds. Many-to-many relationships are compared as memberships, without assuming identical database row order.

Sessions were deliberately excluded, so the destination requires a fresh login. Generated permissions and content types were reused through natural keys rather than copying SQLite-specific IDs.

Import safeguards

  • The branch name in the connection file must match the requested branch.
  • TLS and an up-to-date destination schema are required.
  • Default mode is preflight only. Writes require --apply.
  • A destination with application records is rejected unless it already exactly matches the snapshot. Matching migration-seeded categories are allowed.
  • An already matching destination is a verified no-op; a different populated database is never overwritten automatically.

Backup and rollback limits

The SQLite snapshot and export fixture remain under .backups/, with private directories (700) and files (600). They contain account and MFA secrets and are not encrypted by the script.

SQLite remains intact as a backup; the current server now uses Neon. There is no continuous synchronization. Once PostgreSQL receives new edits, reverting to SQLite requires copying or reconciling those edits first.

This local backup is not a production backup policy. Automated backups and a restore test remain release work.
